## 已接通的主要链路

| 链路 | 当前源码能够确认的行为 | 验证边界 |
|---|---|---|
| 广播 → 暂存/Journal | 受控 I/O 处理，加密暂存或 Journal 提交后正常结束广播持有；独立看门狗记录超时未确认 | 极端存储、密钥和线程资源故障不能保证留存；令牌释放不是业务成功确认 |
| Provider → Room | 接收先尝试保存，最小事务写消息、会话和未读；联系人展示补全另行执行 | 系统默认短信权限及 ROM 行为仍需真机验证 |
| Room → 两套主页 | 观察数据库变化；合并连续请求，不取消正在执行的读库 | 60ms 是调度间隔，不是完整屏幕绘制的实测上限 |
| 收信 → 转发 | 页面绘制不是前置条件；过滤、原始任务与 SIM 快照保护仍保留 | 规则需要的联系人判断仍不可绕过；未知网络结果不自动重发 |

| 通知与已读 | 持久化通知补偿，分别处理发布/抑制回调，可见会话读状态与发布协调 | 仍存在下述过滤竞争及小米通知超时问题 |
| 卡槽与重试 | 优先真实接收证据，未知不猜；执行快照保护旧任务 | 双广播两秒边界和厂商 SIM 参数仍需实测 |
| 保活与远程连接 | 区分设置、启动请求、前台运行和失败；网络变化唤醒已有重连循环 | 不保证用户强停或厂商冻结后立即复活，网络监听不是独立复活机制 |

## 本轮发现的待处理项

### A. 小米灵动岛会同时设置整条短信通知的超时（P1，源码确认）

- 当前 `XiaomiHyperIslandProvider.applyToBuilder()` 调用 `builder.setTimeoutAfter(ISLAND_DISMISS_MS)`，常量为 8000ms（`app/src/main/kotlin/org/fossify/messages/helpers/liveisland/XiaomiHyperIslandProvider.kt:28`、`:72`）。
- `LiveIslandCoordinator` 将该适配器应用到 `NotificationHelper` 的普通短信通知 Builder。触发条件是启用灵动岛且 ROM 被识别为支持小米适配。
- 这不只是 `param_island.islandTimeout` 的岛展示时长，还给整条通知设置了系统超时；未读通知存在约 8 秒后消失的路径。不是所有手机或默认关闭状态都会触发。
- 旧 `android-sms-forwarder-incoming-fix` 工作区已经有删除该 Builder 超时的未提交修改，但当前 1.2.8 没有包含它。
- 建议只保留岛展示时长，不给正常收信通知设置整体超时，并补充开启/关闭灵动岛时未读通知保留的回归。

### B. UI 专用补偿找到目标短信后，未必能将其补入 Room（P2，主机故障场景复现）

- `IncomingSmsUiSyncWorker.kt:127` 找到 `matchingId` 后，只调用默认 `syncThreadToLocal(matchingThread)`。
- 默认窗口是 `MESSAGES_LIMIT = 50`，且未传 `requiredSmsIds`。同一会话又来了更多短信时，已经定位到的旧目标可能落到最近 50 条之外。
- 恢复扫描路径已经使用 `requiredSmsIds` 和严格核验；UI 专用补偿没有接上同一机制，因此可能反复重试直到失败。
- 本轮临时主机验证编译了实际 `IncomingSmsUiSyncWorker`，模拟 Provider 与最近 50 条 Room 同步边界：同会话 60 条短信，目标为第 1 条时，首次返回 retry、达到重试上限返回 failure，目标仍不在本地；目标第 60 条返回 success。
- 这是边界模拟，不是真机实验。它证明专用补偿没有保证目标入库；不能据此断言其他恢复/全量同步路径也无法补齐，更不能称为系统短信已丢失。
- 建议向同步传递已匹配的目标 ID，并使用严格读取和目标落库核验，保持只读修复不转发的职责。

### C. 新的过滤短信可能抑制较早的正常短信通知（P2，静态竞态路径，尚未真机复现）

- 正常接收先保存 Room，之后过滤；过滤短信也留在消息表，但不会进入正常通知发布队列。
- `NotificationHelper.kt:225` 至 `:244` 用 `getLatestUnreadInboxMessage(threadId)` 判断是否被更新消息替代。该 DAO 查询不区分过滤规则或是否存在可发布通知。
- 条件场景：正常消息 A 的异步通知尚未真正发布；同会话更新的过滤消息 B 已入 Room。A 会因 B 更新而被抑制，B 自身又不会通知；抑制回调会将 A 的补偿项结束。
- 原本防止旧通知覆盖新通知的目标有效，但替代条件过宽。建议依据实际可发布/已发布的后继通知证据，而非任意更新的未读消息。

### D. 验证码弹窗有设置属性，但缺少可操作开关入口（P2，静态确认）

- 当前 `Config.showVerificationCodePopup` 默认 true；`IncomingCodeAlerts.popup()` 会读取这个值。
- 当前源码中没有设置界面对该属性赋值。旧工作区 `DeveloperSettingsCard` 已有 Toggle 草稿，但未进入当前 1.2.8。
- 前台验证码事件和复制提示已接通，缺的是入口；不能在日志里宣称已经提供可开关的设置。
- 建议把开关接入实际使用的设置入口，再验证两套主页对同一偏好值的一致性。

## 验证与结论

- `f306962` 的 [Actions 41419411464](https://github.com/2756826865/android-sms-forwarder/actions/runs/41419411464)成功；69 项 SQL、20 个 UI 补偿模拟、18 个联系人故障场景通过；新增 5 项 JVM 回归纳入单元测试；Android 15/16 各 29 项所选测试无失败、错误或跳过。签名 APK 校验和上传成功，正式 Release 步骤跳过。
- 本轮额外执行了上面的 UI 补偿窗口故障场景；没有修改业务源码，没有触发新构建，也没有把静态竞态称作真机复现。
- 先前的刷新饥饿、广播等待保护和联系人首次读库重试，已接入生产调用路径，不能把它们视作完全没有作用。但上述四项还需处理或确认，当前不足以宣布“全部联动无问题”。
- 本次只在活动 1.2.8 工作区写更新日志、发布说明草稿和本复查记录。main、正式 Release 和其他旧工作区均保持原状。普通覆盖升级与跨版本降级不同；接收数据库已到 schema 7，不能把安装旧 APK 当成安全回滚方式。

| C · 过滤消息压制旧通知 | 只比较同会话实际仍在通知栏的已发布消息元数据，候选已读仍抑制，取消不作用于其他消息 | 4 项 JVM 测试覆盖无已发布证据、回调倒序、相同时间与不同会话、未知时间 |
